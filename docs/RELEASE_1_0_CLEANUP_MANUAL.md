# 대국 1.0 출시 전 정리 매뉴얼

이 문서는 대국 1.0 출시 전 저장소 정리, 테스트 정비, 내부 진영 ID 변경,
코드 정리, UI 흐름 점검과 출시 검증의 작업 순서 및 완료 기준을 정한다.

## 1. 기본 원칙

- 현재 동작을 바꾸는 기능 작업과 구조만 바꾸는 정리 작업을 같은 커밋에 섞지 않는다.
- 한 단계의 필수 검증이 실패하면 다음 단계로 넘어가지 않는다.
- 삭제 전에는 참조 여부, Git 추적 여부, 다른 브랜치의 고유 커밋 여부를 확인한다.
- 게임 규칙과 서버 권위 판정은 UI 정리 과정에서 변경하지 않는다.
- 새 의존성은 필요성과 대안을 먼저 검토하고 사용자 승인 없이 추가하지 않는다.
- 비밀값, 로컬 로그, 테스트 산출물과 개인 환경 파일을 커밋하지 않는다.
- 과거 실험 자료와 회귀 재현 자료는 오래됐다는 이유만으로 수정하거나 삭제하지 않는다.
- 모든 변경은 작고 되돌릴 수 있는 커밋으로 나눈다.

## 2. 1.0의 공식 명명 규칙

사용자 화면과 내부 코드 모두 흑과 백을 기준으로 한다.

| 구분 | 1.0 표준 |
| --- | --- |
| 한국어 UI | `흑`, `백` |
| 영어 UI | `Black`, `White` |
| 내부 진영 ID | `black`, `white` |
| 기존 내부 ID | `red`, `blue` — 신규 상태에서는 사용하지 않음 |
| WebSocket 프로토콜 | 버전 3 |
| JSONL 대국 기록 | 새 스키마 버전에서 `black`, `white` 사용 |

색상 CSS 값, 그림 자체의 색, 외부 자료의 고유 명칭은 진영 ID가 아니다. `red`와
`blue`를 기계적으로 전체 치환하지 않는다.

## 3. 변경하지 않는 역사 자료

다음 자료는 재현성과 감사 가능성을 위해 원본을 유지한다.

- `artifacts/`의 과거 AI 대국 및 분석 결과
- `experiments/`의 과거 측정 결과
- 과거 실패 국면을 재현하는 회귀 fixture
- 이미 작성된 개발 기록과 AI 판단 근거

역사 자료를 현재 코드에서 읽어야 한다면 원본을 고치는 대신 입력 변환기를 둔다.

## 4. 작업 단계

### 단계 0 — 기준선 고정

- `main`과 `origin/main`의 동기화를 확인한다.
- 작업 트리가 깨끗한지 확인한다.
- 전용 정리 브랜치에서 작업한다.
- 현재 전체 테스트와 브라우저 테스트 결과를 기록한다.

완료 조건:

- 기준 커밋을 식별할 수 있다.
- 실패 중인 기존 테스트가 없다.
- 정리 작업이 `main`과 분리돼 있다.

### 단계 1 — 테스트 체계 정리

테스트를 다음 책임으로 분류한다.

- `rules`: 엔진 규칙과 상태 전이
- `protocol`: 서버·클라이언트 계약과 정보 은닉
- `ui-behavior`: 사용자 행동과 화면 전환
- `ui-layout`: 잘림, 오버플로와 반응형 배치
- `regression`: 과거 실제 버그의 재발 방지
- `compatibility`: 구버전 저장 데이터와 프로토콜 입력

정리 원칙:

- `app.js`나 HTML 문자열을 정규식으로 검사하는 테스트를 실제 함수 또는 브라우저
  동작 검사로 교체한다.
- 하나의 긴 E2E 테스트가 문구, 레이아웃과 게임 규칙을 모두 책임지지 않게 분리한다.
- 삭제된 DOM ID가 없다는 검사보다 사용자가 더 이상 강제 확인창을 보지 않는 행동을
  검증한다.
- 시각 테스트가 스냅샷 비교를 하지 않는다면 이름과 설명에 그 사실을 반영한다.
- 과거 호환성 테스트와 현재 제품 동작 테스트를 구분한다.
- 온라인 PvP의 방 생성, 참가, 진영 결정, 액션, 재대국을 실제 WebSocket 통합
  테스트로 보강한다.

완료 조건:

- 구조 정리만으로 실패하는 소스 문자열 결합 테스트가 없다.
- 핵심 사용자 흐름과 서버 계약의 담당 테스트가 명확하다.
- 전체 테스트가 통과한다.

### 단계 2 — 진영 ID 마이그레이션

순서는 다음과 같다.

1. 엔진 상수, 새 상태, 액션, 이벤트와 정보 은닉을 `black`/`white`로 변경한다.
2. AI, 퍼즐, 튜토리얼과 로컬 어댑터를 변경한다.
3. 렌더러, 앱 상태, DOM의 의미상 클래스와 접근성 문구를 변경한다.
4. 서버 방 상태와 WebSocket 메시지를 프로토콜 버전 3으로 변경한다.
5. JSONL 기록 스키마를 올리고 구버전 `red`/`blue` 기록 입력 변환을 제공한다.
6. 테스트와 현재 실행 스크립트를 변경한다.
7. 문서를 현재 계약과 맞춘다.

호환성 규칙:

- 새 클라이언트와 새 서버는 `black`/`white`만 송수신한다.
- 프로토콜 버전이 맞지 않으면 명시적인 오류를 반환한다.
- 지원하기로 한 구버전 JSONL은 입력 경계에서만 변환한다.
- 내부 상태에 `red`/`blue`와 `black`/`white`가 동시에 존재하지 않게 한다.

완료 조건:

- 실행 코드와 신규 테스트 fixture의 내부 진영 ID가 `black`/`white`다.
- 숨은 특수 기물 정보가 반대 진영에 노출되지 않는다.
- 색상 반전 대칭 테스트가 유지된다.
- 실제 두 클라이언트 온라인 대국이 동작한다.
- 구버전 기록에 대한 지원 또는 명시적 거부 정책이 테스트된다.

### 단계 3 — 폴더, 파일과 브랜치 정리

- 병합된 작업 브랜치를 로컬과 원격에서 정리한다.
- 고유 커밋이 있는 브랜치는 삭제하지 않고 분류한다.
- 과거 독립 서버 저장소가 현 모노레포에 완전히 흡수됐는지 확인한다.
- 상위 작업 폴더의 이미지와 임시 파일을 `사용`, `보관`, `삭제 후보`로 분류한다.
- 추적되지 않아야 하는 생성물은 `.gitignore`에 반영한다.
- `.DS_Store`, 로그, 테스트 결과와 캐시를 저장소에서 제외한다.

완료 조건:

- 각 저장소와 상위 폴더의 역할이 명확하다.
- 삭제된 자료의 대체 위치나 불필요 판정 근거가 있다.
- 작업 트리에 불명확한 파일이 없다.

### 단계 4 — 코드 정리

다음 순서로 진행한다.

1. 참조가 없는 함수, 상수, 번역 키와 CSS 선택자를 삭제한다.
2. 타이머와 세션 초기화의 반복 코드를 통합한다.
3. 모드별 공유 액션과 결과 처리의 중복을 통합한다.
4. 개발용 demo 상태 생성을 운영 흐름에서 분리한다.
5. `app.js`에서 결과 UI, 특수 발동, 튜토리얼, 세션 초기화 책임을 점진적으로
   모듈로 분리한다.

완료 조건:

- 같은 상태를 서로 다른 코드 경로가 다르게 초기화하지 않는다.
- 미사용 코드와 과거 UI 잔여물이 없다.
- 모듈 경계가 게임 규칙, 화면 표현과 서버 통신의 책임을 구분한다.
- 기능 및 레이아웃 회귀가 없다.

### 단계 5 — UI 흐름 정리

다음 사용자 여정을 한국어와 영어로 확인한다.

- 첫 실행 → 튜토리얼 → 로비
- 로비 → AI 설정 → 대국 → 종료 → 결과 → 재대국/로비
- 챌린지 목록 → 대국 → 성공/실패 → 재시도/다음
- 온라인 대기실 → 방 생성/참가 → 진영 결정 → 대국 → 재대국
- 설정 → 저장 → 다시 열기

각 화면에서 확인할 항목:

- 주 행동이 하나로 분명한가
- 뒤로가기, 닫기, 홈과 재시도 행동이 일관적인가
- 같은 의미의 용어가 화면마다 다르게 쓰이지 않는가
- 확인 없이 실행하면 위험한 행동과 불필요한 확인창이 구분되는가
- 모바일, 태블릿, 데스크톱에서 문구와 버튼이 잘리지 않는가
- 키보드 포커스, 대화상자 이름과 라이브 알림이 올바른가

완료 조건:

- 막다른 화면과 중복 행동이 없다.
- 핵심 흐름을 브라우저 테스트가 보호한다.
- 지원 화면 크기와 두 언어에서 레이아웃 오류가 없다.

### 단계 6 — 출시 검증

필수 자동 검증:

```bash
npm test
npm run test:browser
npm run build:mobile
node --check app.js
git diff --check
```

필수 수동 검증:

- 새 브라우저 저장 공간에서 첫 실행
- 흑과 백 각각으로 AI 대국 시작
- 세 특수 기물 발동과 마법사 순간이동
- 왕 포획, 기권, 시간 초과와 둘 곳 없음 종료
- 경기 결과, 재대국과 로비 복귀
- 두 브라우저를 이용한 온라인 대국
- 한국어와 영어 전환 및 설정 유지

출시 조건:

- 필수 자동·수동 검증이 모두 통과한다.
- 심각도 높은 미해결 결함이 없다.
- `README`의 설치, 실행, 테스트와 프로토콜 설명이 실제 코드와 일치한다.
- 버전과 출시 커밋을 식별할 수 있다.
- `main`과 배포 대상이 같은 커밋을 가리킨다.

## 5. 커밋 규칙

권장 커밋 순서:

1. `docs: define the 1.0 cleanup and release manual`
2. `test: decouple cleanup coverage from implementation text`
3. `refactor(engine): rename side ids to black and white`
4. `feat(protocol): migrate side ids and version the wire contract`
5. `refactor(ui): adopt black and white side ids`
6. `refactor: remove dead code and consolidate lifecycle cleanup`
7. `test: cover 1.0 UI and online match flows`
8. `docs: finalize 1.0 runbook and release notes`

각 커밋은 해당 범위의 테스트를 통과해야 하며, 전체 검증 결과는 최종 커밋 전에 다시
확인한다.

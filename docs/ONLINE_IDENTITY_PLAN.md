# 온라인 계정·재접속·전적 구현 계획

2026-09-06 · 설계안, 서버 기능은 아직 구현하지 않음

## 확정 UI

모드·등급 상단 바 제거. 기존 턴 카드 안에 온라인 모드에서만 `상대 연결`+초록 점 / `연결 끊김`+빨간 점을 표시한다. 영어는 Connected / Disconnected. 턴·시간은 유지한다. 이 표시는 현재 연결 상태를 반영하며 자동 재접속 구현을 의미하지 않는다.

## 현재 상태

server/server.js는 메모리의 rooms Map과 socket.membership으로 방·흑백 자리를 관리한다. 연결 종료 시 leaveRoom을 호출한다. 서버가 규칙과 승패를 판정하고 플레이어별 숨김 상태를 제공한다. 지속적 계정 인증과 재접속 소유권, 영구 전적 DB는 별도로 구축해야 한다. 실제 배포 서비스가 이 모노레포를 사용하는지도 착수 시 확인한다.

## 단계 1 — 게스트 ID와 인증

- 서버 발급 player_id(UUID), 변경 가능한 nickname, 고유 public_code를 분리한다. 공개 코드와 방 코드는 인증 수단이 아니다.
- 자동 별명으로 즉시 시작. 닉네임은 길이·문자·금칙어 정책을 검증하고 HTML이 아닌 텍스트로 표시한다.
- 게스트 생성 시 서버가 암호학적 난수 자격 증명을 발급한다. 접근 토큰은 짧게 유지하고 갱신 토큰은 회전·폐기 가능하게 하며 서버에는 해시만 저장한다.
- iOS Keychain/Android Keystore 기반 보관을 사용한다. 브라우저는 HTTPS HttpOnly Secure 쿠키와 Origin 검증을 사용하는 별도 전달 방식을 설계한다. 토큰을 URL·로그에 넣지 않는다.
- WebSocket 연결은 인증 완료 전 경기 요청을 받지 않는다. Origin 검사는 인증을 대신하지 않는다. 모든 메시지는 서버가 확인한 player_id에 귀속시킨다.
- 향후 Apple/Google 등 로그인 식별자를 같은 player_id에 연결할 수 있도록 identity 테이블을 분리한다. 서로 다른 계정의 전적을 자동 합산하지 않는다.
- 게스트는 미연결 상태에서 삭제·분실 시 복구가 어려울 수 있음을 안내한다. 순위 경쟁과 다중 계정 악용 대책은 로그인 연결 정책과 함께 정한다.

DB 초안: players(id, public_code UNIQUE, nickname, created_at, status), identities(player_id, provider, subject UNIQUE), sessions(id, player_id, refresh_hash, expires_at, revoked_at).

완료 기준: 앱 재실행 시 같은 ID, 위조·만료·폐기 토큰 차단, 타인 ID로 방 접근 불가, 비밀값 로그 미노출. 운영 반영 전 로컬·스테이징 검증.

## 단계 2 — 재접속과 전적

- 매치는 socket 대신 player_id에 자리를 부여한다. 동일 계정 중복 접속은 기존 연결 교체 등 단일 정책으로 처리한다.
- 끊김 후 유예 시간은 제안값 60초. 서버 시간으로 관리하며 기존 턴 시간은 계속 흐르게 해 고의 끊김 이득을 막는다. UX에는 카운트다운을 추가하지 않는다.
- 재접속 시 인증된 매치 참가자만 최신 개인별 snapshot과 revision을 받는다. 다른 플레이어의 숨겨진 상태를 보내지 않는다.
- 요청에 action_id와 expected_revision을 포함해 중복·이전 요청을 거절하거나 동일 결과를 반환한다.
- 서버 종료 복구를 위해 매치 이벤트·스냅샷·기한을 저장한다. 운영 중단에 의한 패배와 실제 유저 이탈을 구분하는 무효 경기 정책을 둔다.
- matches, match_players, match_actions 테이블. 경기 결과 기록은 match_id 기준 단 한 번, 트랜잭션으로 확정한다. 클라이언트가 승패·점수를 제출하여 확정할 수 없다.
- 랭킹은 확정 경기에서 파생한다. casual/ranked 구분과 rating_events의 match/player 유일성으로 이중 반영 방지. Elo 등 산식과 참가 자격은 별도 확정 전 적용하지 않는다.

완료 기준: 두 기기 끊김·재접속, 중복 연결·중복 요청, 서버 재시작, 동시 종료 상황에서 상태·승패·전적 일치.

## 단계 3 — 보안 검증 및 출시 게이트

HTTPS/WSS, 허용 Origin, 메시지 스키마·크기·속도 제한, 계정/IP별 연결·방 생성 제한, 방 참가 권한, 숨김 정보 미노출, 토큰 회전·재사용 차단, 경기 결과 중복 방지, 비정상 접속 기록을 검증한다. IP만으로 사용자 신원을 판단하지 않는다. 계정·전적 보존/삭제 정책과 개인정보 안내, DB 백업·복구·운영 비밀 관리도 배포 전에 준비한다.

참고: https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html

## 작업을 끊는 지점

이번 작업은 UI와 이 설계 문서, iOS 동기화까지다. 다음 단계는 인증과 영구 DB를 도입하는 별도 작업이다. DB 호스팅·비용, 기기 보안 저장 라이브러리(새 의존성 승인), 게스트 계정 복구 방식, 재접속 정책을 확정해야 한다. 계정 생성 API 자체의 남용 제한은 인증 구현 때부터 넣는다. 최종 보안 단계로 미루지 않는다.

다음 요청 예시: “docs/ONLINE_IDENTITY_PLAN.md를 기준으로 1단계 게스트 ID·인증을 구현하자. 현재 배포 환경과 DB 선택지부터 확인하고, 새 의존성과 비용이 필요한 부분은 설명해줘. 랭킹 확장을 고려하되 운영 배포는 별도로 진행하자.”

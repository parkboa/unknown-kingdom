# 온라인 인증 지연 진단 — 2026-10-03

## 결론과 확실성

**후속 단서: 사용자가 `rate limited` 인증 오류를 보고했다.** 배포된 커밋
`7f7b702`에도 있는 서버 자체 제한은 일반 인증 요청 30회/분, 새 게스트 생성
시도 5회/시간이다. 같은 연결 상대 주소로 여섯 번째 신규 생성 시도를 넣었을 때
`429 / RATE_LIMITED`를 모의 재현했다. 촬영 중 계정 삭제·신규 생성을 반복한
상황과 부합하며, 이번 오류는 무료 플랜 한도보다 앱 서버 자체 제한일 가능성이 높다.
다만 일반 30회 제한과 신규 생성 5회 제한은 같은 오류를 반환하므로 실제 요청의
어느 제한이 발동했는지는 원본 응답/요청 기록 없이는 확정할 수 없다.

`req.socket.remoteAddress`로 제한을 묶으므로 서로 다른 사용자가 같은 중계 서버
연결 주소를 공유하면 제한도 공유한다. 모의로 서로 다른 forwarded 주소를 넣어도
같은 peer면 6번째에 차단됐다. 이는 그대로 출시할 경우 정상 사용자들이 서로의
한도를 소진할 수 있는 구조적 문제다. 실제 촬영 요청의 peer 주소는 확보하지 않았다.
유료 플랜으로 바꿔도 코드에 설정한 5회/30회 제한은 자동 변경되지 않는다.

실기기 영상의 재실행 전 지연을 **Supabase Auth 자체의 처리 지연으로 확정할 증거는 없다**.
앱의 인증 전 대기와 WebSocket 연결 처리에서 제한 없는 대기가 가능한 경로를 확인했다.
해당 경로를 모의 조건으로 막으면 재시도도 같은 미완료 인증 작업을 기다리거나
온라인 화면이 계속 `connecting`에 머문다. 이는 코드의 회복 처리 빈틈을 재현한 것이며,
실제 iPhone에서 같은 단계가 막혔다는 증명은 아니다.

현재 백엔드는 정상 응답한다. 별도로 Render 무료 인스턴스의 유휴 기동 지연과
앱의 15초 인증 HTTP 제한이 맞지 않는 운영 문제가 있다. 다만 촬영은 서로 몇 분
간격이고, 촬영 시간대 Render 로그에 재기동이 보이지 않아 이번 녹화의 원인으로
단정하지 않는다.

## 코드에서 확인한 대기 경로

1. `js/auth.js`: `navigator.locks.request`에서 인증 작업 차례를 기다리는 부분에는
   제한 시간이 없다. `inflight`를 공유하므로 한 번 미완료 상태가 되면 메뉴 재진입의
   `getSession()`도 그 작업을 기다린다.
2. 같은 파일의 iOS Keychain 플러그인 `get`/`set` 및 CAPTCHA 브리지 응답을 기다리는
   부분에는 JS 측 제한이 없다. Native CAPTCHA 화면 자체에는 180초 타이머가 있다.
   일반 HTTP 요청의 15초 제한은 이 선행 단계들을 포함하지 않는다.
3. `js/network.js`: WebSocket `open`과 서버의 `authenticated` 응답에 클라이언트
   대기 제한이 없다. 서버는 연결이 열린 뒤 20초 인증 제한을 두지만, 그 전에 연결이
   열리지 않는 경우에는 도움이 되지 않는다. 최초 대기실 진입에는 대국 재접속과 같은
   자동 복구가 없다.
4. `app.js` 시작 화면은 WebSocket 열기를 검사한다. Auth·DB 성공까지 확인하는
   검사가 아니므로 시작 화면 통과가 전체 인증 정상성을 뜻하지 않는다.
5. JS 원본과 로컬 iOS 패키징 자산의 auth/network 파일 SHA-256이 각각 일치했다.
   이미 설치된 TestFlight 바이너리에서 독립 추출해 확인한 것은 아니다.

## 검증과 다음 단계

- 추가 검증: 실제 계정 생성 없이 모의 HTTP handler에 새 게스트 6회 입력 →
  1~5번째 200, 6번째 429/RATE_LIMITED. 같은 조건에서 기존 세션 refresh는 200.
  모의 upstream 429 예외는 현재 서버의 catch에서 401/AUTH_FAILED로 변환됐다.
  따라서 앱의 RATE_LIMITED 표시는 upstream Supabase 오류와 구분할 유력한 단서다.
- 서버 인증 시험 6개 모두 통과. 첫 실행의 HTTP 시험은 샌드박스 로컬 포트 EPERM으로
  실패했으며, 승인된 실행에서 모두 통과했다. 실제 서비스 요청을 남발하지 않았다.
- 우선 수정 검토: 신뢰할 수 있는 중계 경계를 기준으로 사용자를 구분하는 제한 설계,
  제한 종류와 재시도 가능 시각 안내, upstream 오류 구분. 임의 forwarded header를
  그대로 신뢰하거나 제한/CAPTCHA를 제거하는 방식으로 해결하지 않는다. 아직 코드·
  운영 설정을 변경하지 않았다. 촬영은 현재 성공한 계정을 유지하고 추가 삭제/생성을
  반복하지 않는 것이 좋다.
- 기존 auth-client/network-reconnect 시험 10개 통과.
- 임시 모의 진단에서 lock 미승인, Keychain 응답 미완료, WebSocket 미연결을 각각
  주입했다. 160ms 관측 중 앞의 두 경우 재시도도 같은 대기 상태, 마지막은
  connecting 상태 지속을 확인했다. 제한이 없다는 결론은 소스와 함께 판단했다.
- 소스 수정·빌드 업로드·운영 설정·요금제 변경 없음. 진단 도구와 문서만 추가했다.
- 사용자에게 현재 iPhone에서 온라인 진입·메뉴 재진입 결과와 Wi-Fi/셀룰러 환경을
  질문했고 **“아이디 나왔어”**라고 응답했다. 현재 접속 성공은 확인했지만 걸린 시간·
  메뉴 재진입 여부·통신 종류는 응답에 없으므로 즉시 접속했다고 해석하지 않는다.
  지속적인 전체 서비스 장애를 뒷받침하지 않으며, 간헐적 증상의 원인 확정은 남는다.
  반복되면 기기에서 lock → Keychain → 세션 HTTP → CAPTCHA →
  WebSocket → 서버 인증의 단계별 소요 시간을 얻는 진단 빌드가 필요하다.
- 수정 방향은 단계별 제한 시간/오류 구분/안전한 재시도이며, 늦은 응답의 토큰 회전과
  중복 게스트 생성이 생기지 않도록 취소·완료 처리를 설계해야 한다. 단순히 전체
  타이머 만료 후 `inflight`를 지우거나 무조건 새 계정을 만드는 방식은 피한다.
- Render 무료 기동 문제를 없애려면 인스턴스 운영 방식을 별도로 결정한다.
  유료 전환은 이번 진단 요청에 포함되지 않는다.

공식 참고: [Render 무료 인스턴스 유휴 중지와 재기동](https://render.com/docs/free#spinning-down-on-idle).
15분 유휴 뒤 중지되며 재기동에 약 1분이 걸릴 수 있다고 안내한다.

[Supabase Auth 요청 제한](https://supabase.com/docs/guides/auth/rate-limits): 익명 생성은
기본 IP별 30회/시간이며 설정 가능하다. 이 프로젝트의 실제 설정값을 이번에 읽은
것은 아니다. 서버를 통해 인증할 때 사용자 주소를 전달하지 않으면 Supabase 쪽도
서버 주소 기준으로 제한을 공유할 수 있다. 이 또한 우리 서버의 자체 5회 제한과 별도다.
